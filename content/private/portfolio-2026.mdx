# 뱅크샐러드 · 2021.03 ~ 현재

건강 제품 조직 웹 리드(프론트엔드 4명). 2026.04부터 웹 챕터 리드(15명) 겸임. 2024.07 ~ 2025.10 육아휴직.

보험은 상담 연동이 목표이고 보장분석, 보험료 줄이기, 가족력 완벽대비가 상담을 받을 이유를 만드는 하나의 퍼널입니다. 유전자검사는 1.0 런칭부터 2.0 리뉴얼까지 맡았습니다.

## 1. 제품: 완성도 있게 만들고, 매출 구간은 깨지지 않게 지킨다

비개발자 눈에 보이지 않는 개발 관점의 구멍과 엣지케이스를 잡고 가는 것이 개발자의 역할이라고 봅니다. 제품이 완성도 있게 나가는 것을 원하고, 그것을 잘합니다. 매출이 발생하는 구간을 중요하게 관리하는 것은 회사의 목표를 지키는 것과 같고 브랜드와도 이어지므로, 그 구간의 가드는 2중 3중으로 두고 모니터링합니다.

### 완성도: 개발 관점에서만 보이는 것을 개발 전에 결정으로 닫는다

재진입, 상태 조합, 실패, 경계값, 그리고 기존 코드에 이미 있는 정책은 기획서에 빠지기 쉽습니다. 찾는 것 자체는 도구가 대신할 수 있으니 개발자의 몫은 무엇을 물을지 정하고, 그중 PM이 결정할 것을 골라 개발 전에 닫는 것이라고 봅니다. 테크스펙 단계에서 유저의 진입점과 상태값을 축으로 흐름을 그려 그 결정을 앞당깁니다. 검증이 필요한 것은 실험으로, 노출만 제어할 것은 Feature Flag로 나갑니다.

#### 유저로서 먼저 써 보고 고친다

정식 UX 리서치 전에 개발자가 유저로서 먼저 써 보면 걸러지는 것이 있습니다. 당근 모임의 사용자이자 모임장이었던 것도 같은 습관입니다.

- **유전자검사** (2026, 2.0 리뉴얼): FF로 열린 2.0을 유저로서 끝까지 써 보고 UX·폐기·정책 3범주로 피드백을 정리해 PM에게 전달. 1.0을 만든 팀원들이 아는 리스크도 같은 형식으로 모아 PM이 판단할 수 있게 함. 롤아웃 확정 후 1.0 잔재를 7단계 스택 PR로 하루에 정리해 638개 파일에서 26,485줄 순감소
- **보험 · 보장분석** (2026, 5세대 실손 전환): 디자인 리뷰 단계에서 유저 입장으로 직접 써 보고 개선점을 p1·p2·p3 우선순위로 올려 반영, 추가 개선을 적용한 녹화본을 공유해 최종 스펙 결정. 반나절 만에 1차 합의

#### 코드에 남은 정책을 기획으로 되돌린다

기획서보다 코드와 기존 팀원이 더 많이 아는 것이 있습니다. 그 차이를 PM이 판단할 수 있는 형태로 되돌려 개발 전에 닫습니다.

- **보험 · 보험료 줄이기** (2026, 내보험탭 모듈): 기존 코드에는 있지만 기획서에 빠진 정책 4건(재연결 판정·보험가이드·샘플데이터·할인제도)을 테크스펙 단계에서 코드를 역으로 읽어 PM에게 되돌려 확정. 개발 전에 닫혀 개발분 전량을 마일스톤 6일 앞서 제출
- **보험 · 금액 표기 규칙** (2026): PM마다 다르게 기획한 금액 표기(반올림·기준액·노출 단위)가 코드에 흩어져 있어 중복 로직 파일 3개를 프리셋 4종으로 통합하고, 스토리북 비교 테이블을 열어 PM이 코드 규칙을 보고 기획을 맞추도록 역제안. 경계값 테스트 36건. 이후 5,000원 미만이 0원으로 보이던 버그는 반올림 결과가 0이면 원본을 반환하도록 고치고 총액 불일치 허용을 문서화

#### 테스트로 직결

- **보험 · 보장분석** (2026, 5세대 실손 전환): 세대 조합 유즈케이스표를 만들어 테스트 케이스와 MSW 시나리오로 그대로 전환. 선행 실험은 실험군 승리로 종료
- **유전자검사** (2021, B2C 런칭): 신청 진입 검증 API 4개 중 2개를 서버 validation으로 옮기고 entry 컴포넌트에서 UI와 검증 로직을 분리

#### 배포하면서 잡는다

스펙과 테스트로 다 잡히지 않는 것은 1%에서 100%까지 단계별로 올리며 실험군 태그로 에러를 쿼리해 잡습니다. 실험군별 에러 태그를 전 조직에 적용한 이야기는 아래 안정성의 실험 관측 인프라에 있습니다.

- **보험 · 보장분석** (2025 ~ 2026, 리뉴얼): 실험 1 클린업은 실험 2가 그 코드에 의존해 보류를 택함. 후속배포 첫 경험에서 블로커 5개를 2시간 안에 넘기고 절차를 팀 가이드로 남김
- **보험 · 보장분석** (2026, 보장기간 섹션 실험): 실험 설계가 겹쳐 돌아가 복잡도가 높아지고 기존 실험은 p-value가 나오지 않을 상황이라, 기존 실험을 종료하고 클린업한 뒤 새 실험으로 가자고 제안해 PM과 합의

### 안정성: 매출에 닿는 흐름을 지킨다

#### 보험 · 상담 연동 (2023 ~ 2026)

- **해피톡 연동**: 상담신청부터 해피톡 카카오톡 채팅 오픈까지의 프론트엔드 연동을 최초 구성. GA 할당과 약관은 서버와 함께 설계하고, 토큰 3종으로 상담 레코드와 채팅방을 매핑
- **상담 유실을 막는 제약 규명**: 상담 레코드와 채팅방을 잇는 커스텀 파라미터가 조건에 따라 통째로 무시되면 상담이 유실됩니다. 채팅 오픈 API가 HTML을 내려 안에서 JS가 실행되는 구조를 분석해 챗봇 자동발화 이벤트가 걸리면 파라미터가 전부 무시되고 20자 제한과 구분자 문자에 유실된다는 제약을 밝혀 문서화
- **실패한 상담을 되찾는 절차**: 전환 오류 장애 뒤, 같은 일이 다시 나도 상담을 잃지 않도록 감지 → 원인 분류(뱅샐 웹·해피톡 서버·스펙) → 처리 절차를 가이드라인으로 만들고, 전환 실패 유저를 추적할 수 있게 채널 UID를 양쪽에 저장. 외부사 커뮤니케이션은 고객사인 GA에 위임한다는 원칙 수립
- **가족력 완벽대비** (2026): 보험료 줄이기·보장분석처럼 보험 제품 하나로 가족력 맥락을 떼어 낸 신규 제품. 스캐폴딩부터 입력·동의·결과 화면, 보험상담 연결까지 단독 구현해 상담 진입 경로를 하나 더 만듦

#### 유전자검사 (2021)

- **B2C 런칭** (2021): 유전자검사를 신청·검사·결과 조회 서비스로 처음부터 B2C로 열며 웹 메인 개발. 선착순 운영에서 VoC가 가장 예민했던 것이 카운트다운 타이머로, 같은 시각에 들어온 유저들의 남은 시간이 서로 다르게 보인다는 문의가 왔음. 1초씩 빼는 setInterval 대신 서버가 준 남은 시간을 절대값으로 두고 requestAnimationFrame timestamp로 경과 시간을 계산하는 타이머로 바꿔 기기와 탭 상태에 관계없이 같은 시각에 같은 숫자가 보이게 함. 반송·타임라인·결과 페이지

#### 매출 여정을 지키는 주체, 측정, 온콜

매출 구간은 숫자로 지킵니다. 누가 지키는지를 먼저 정하고, 측정이 틀어지면 지키는 것도 틀어지므로 실험 배정과 이벤트 같은 측정 자체를 감시하고, 2주 로테이션 데일리 온콜에서 이상 징후를 먼저 보고 대응합니다.

- **매출 여정을 지키는 책임 주체 신설** (2026): "매출 직결 여정 보호, 유입 컨텍스트를 전환까지 운반"을 원칙으로 라우팅 영역 책임 그룹을 신설하고, 책임 범위와 운영 단계를 스펙으로 정의
- **실험 관측 인프라: 보이지 않던 실패를 보이게** (2026): treatment 100% 롤아웃에도 대조군 유입이 이어지는데 기록이 없던 것을 발견. SDK가 예외를 던지지 않아 "빈 variant"를 신호로 Sentry 계측하고 fetch 실패와 타겟팅 제외를 태그로 구분. 14일간 110,455건(66,595명)이던 오탐을 원인별로 error·warning·미보고로 분리하고 fetch 전용 prefetch API를 노출해 오용 경로 제거, 배포 직후 시간당 420~500건에서 10~20건으로, 신규 릴리즈에서는 0건. 실험군 태그를 조회 경로가 수렴하는 한 곳에 세팅해 호출부 수정 없이 전 조직 적용
- **온콜 아침 체크리스트와 리포트 4종** (2023 ~ 2026): 2주 로테이션 데일리 온콜이 사람의 기억에 의존하지 않도록, 매일 9시 슬랙 워크플로가 온콜 담당자에게 배포 후보군 업로드, Sentry 이슈 확인, 404 확인, Amplitude 이상 지표 확인 4단계를 보내고 완료 이모지로 닫게 함. 각 단계에는 배포 티켓 자동 추출, Sentry 전일 대조, 404 집계 스킬, Amplitude 이상 징후 리포트가 자동으로 붙어 사람은 확인과 대응만 함. 보험 매출 퍼널 Amplitude 대시보드는 2023년에 혼자 만들었고, 2026년 보안 검토에서 API 키 방식이 불허되자 Custom Agent로 경로를 바꿔 매일 10시에 리포트가 도착하게 함. 매출 중요도가 높은 퍼널 대부분을 포함
- **이중 모니터링** (2026): 이벤트 누락이 한 달 방치된 사례를 계기로 코드 레벨 + Amplitude 이중 모니터링을 제안
- **웹 성능 지표 수집** (2022): Web Vitals를 수집해 BI에 연결하는 인프라를 만듦. 지표 기반 개선은 기술부채 해소를 앞에 둔 팀 OKR 우선순위에 밀려 진행하지 못함

## 2. 유저: 앱 안팎에서 거쳐 오는 경로를 안다

유저가 앱에서 화면에 닿기까지의 과정을 알아야 문제가 생겼을 때 디버깅이 되고 UX를 개선하려 할 때 어디를 어떻게 조사할지 알 수 있습니다. 앱 밖에서는 검색으로 들어오는 탐색 유저가 있습니다. 목적이 분명한 유저라 목적을 앱에서 이룰 수 있으면 앱 전환으로 이어지고, 이 풀은 트렌드를 읽는 창이기도 합니다. 굿닥에서 대표가 SEO 강의까지 지원하며 강조한 것을 지금 회사에서는 혼자서라도 모니터링하고 PM에게 전파했습니다. 웹에서 앱으로 유저를 보내는 방법은 2019년에 [딥링크 글](https://feel5ny.github.io/2019/09/22/Communication_001/)로 정리한 뒤로 계속 다뤄 온 주제입니다.

### 앱 안: 유저가 화면에 닿기까지의 레이어

유저가 화면에 닿기까지 네이티브 라우팅, 인프라와 서버, 클라이언트 데이터, 렌더링 층을 지납니다. 인프라를 직접 관리하지는 않지만 proto로 정의된 API·브릿지 계약(정의에 기여), Docker·k8s 배포, SSR 서버 위에서 5년간 제품을 만들며 어느 층에서 문제가 나는지 알아야 원인까지 내려갈 수 있고 에러가 났을 때 서버·인프라·SDK 중 어디로 보낼지 정할 수 있다는 것을 배웠습니다.

#### 네이티브가 여는 웹뷰: 라우팅

앱이 웹뷰를 어떻게 열고 닫는지 알아야 그 경계의 문제를 잡을 수 있습니다.

- **iOS·Android 오픈 방식 차이** (2023): 보장분석에서 연결관리로 넘어가는 퍼널에서 iOS는 딥링크, Android는 openView로 열어 인코딩이 이중 적용되던 버그. openView는 미인코딩으로 고치고 실험키로 iOS도 통일
- **웹뷰 히스토리와 네이티브 닫힘** (2026): 수정 페이지에서 뒤로가기하면 웹뷰가 닫히던 문제. 전 구간이 replace 체인이라 히스토리 depth가 0이고, depth 0의 뒤로가기는 네이티브가 웹뷰를 닫는 동작이었음. 결과→수정은 push, 제출 후 back으로 바꿔 해결하고, replace로 결과를 다시 쌓는 방법은 "결과에서 뒤로가기 한 번에 닫힘" 정책이 깨져 기각

#### 데이터 층: 캐시와 서버 상태

서버 응답이 화면에 닿기 전에 지나는 클라이언트 캐시에서 생기는 race와 옛 값 문제는 데이터의 성격을 근거로 풉니다.

- **플랫폼별 문제 상황 파악** (2026): 웹뷰 mutation이 요청도 에러도 없이 무한 로딩되던 문제를 재현해, react-query 특정 버전의 networkMode 오류와 iOS 시뮬레이터가 onLine을 잘못 내려주던 두 원인으로 좁혀 해결
- **데이터 정합성**: write-once 데이터 성격을 근거로 `staleTime: Infinity` + `cancelQueries`로 race 해결
- **캐시 전략**: `useState` 스냅샷 구조라 invalidate 대신 `removeQueries`로 교체. 다른 화면에서는 refetch 완료 전 재진입 race 때문에 `setQueryData` 즉시 동기화를 택함

#### 렌더링 층: 원인까지 내려간다

- **React children** (2026): `Children.toArray`가 Fragment를 풀지 않는 점을 재귀 평탄화로 해결, 재현 테스트 추가
- **CSS line box** (2026): 공백 노드가 line box를 만들지 않아 baseline이 어긋나는 문제를 nbsp로 해결, 공용 컴포넌트라 4곳 동시 해소

### 앱 밖: 오가닉·오프라인·CRM 채널에서 오는 유저를 데려온다

앱 밖 유입은 돈을 내지 않는 오가닉(검색)과 자사 유저에게 직접 보내는 CRM(앱 푸시·알림톡)으로 나뉩니다. 일상의 검색이 유입 풀이 된다는 것을 아는 개발자는 생각보다 적고 모바일 퍼스트 조직일수록 이 풀을 간과합니다. CRM 채널은 진입 페이지가 앱 밖 플랫폼마다 생기므로 그만큼 지켜야 할 구간이 됩니다.

#### 오가닉: 검색 유입 경로 신설과 자동화

- **health 전체 인덱싱 정리** (2025-12): sitemap이 없어 의도한 페이지는 색인되지 않고, 본인인증·상담신청 과정 페이지는 오히려 검색에 노출되어 오가닉 유저 UX와 브랜딩 리스크가 있던 상태. 검색 스코어링이 시간에 따라 쌓이는 구조라 다른 부채보다 우선순위를 올려 혼자 먼저 정리. 노출할 페이지는 sitemap 추가와 콘솔 재제출, 막을 페이지는 robots 처리와 색인 제거로 검색 결과를 의도한 페이지 위주로 정상화하고, 문제·조치·임팩트를 PM에게 서면으로 공유
- **보험 · 보험료 줄이기 web** (2025): 앱 전용 솔루션에 웹 버전을 만들며, PM이 잡은 SEO 메타 스펙에 "검색 노출이 목적이면 메타만으로는 안 되고 이 페이지들은 색인 요청이 없어 검색봇이 못 들어온다"고 짚어 sitemap 등록을 같이 진행. PL 요청으로 보험진단 전체 인덱싱 점검을 맡고, 스펙마다 색인이 챙겨지도록 보험 PM 가이드가 필요하다고 제기. 이것이 이듬해 PM SEO 강의로 이어짐
- **네이버 미색인 진단과 색인 자동화** (2026): 네이버 검색 로직 변경 뒤 콘텐츠 유입이 급감했다는 마케터 문의에, 색인·노출·트래킹 세 단계로 진단 틀을 잡아 트래킹은 정상임을 걸러 내고 SERP 개편을 원인으로 좁힘. 손댈 수 있는 SEO 경고 개선과 dateModified JSON-LD를 배포한 뒤, 템플릿 변경으로 전 페이지 재색인이 필요해지자 벌크 요청 스크립트와 IndexNow 연동으로 신규·수정 페이지 색인 요청을 자동화

#### 오프라인: 검사 키트의 QR에서 오는 유저

- **유전자 키트 QR 브릿지 페이지** (2023): 추가검사 키트에 인쇄되는 QR이 목적지 URL을 직접 가리키면 URL이 바뀔 때 이미 배포된 키트를 되돌릴 수 없어, 팀이 제어하는 브릿지 웹 페이지를 한 단 두고 거기서 포워딩하자고 제안하고 구현. 지금은 그 페이지가 Airbridge 링크로 넘겨 추가분석 약관 동의 페이지에 도착하게 함

#### CRM: 앱 푸시와 알림톡에서 오는 유저

- **상담 진입 경로가 앱 밖으로 넓어짐** (2023 ~ 2024): PM이 상담 진입 경로를 알림톡 유입 브릿지, 실손·건강검진 앱 푸시 캠페인 인앱 페이지, 상담사용 웹뷰로 넓히면서 CRM 영역까지 매출 구간이 됨. 앱 밖 플랫폼마다 진입 페이지를 구현하고, 지켜야 할 모니터링 범위를 그만큼 넓힘

## 3. 팀: 개인이 떠안던 비용·실수·결정을 팀의 절차로 옮긴다

사람은 성향이 다르고, 그것을 한 방향으로 움직이게 하는 것은 결국 시스템입니다. 잦은 실수는 누구에게나 생기므로 시스템이 막게 하고, 사람은 그 위에서 더 성숙한 구간으로 올라가게 하는 것이 시스템의 역할이라고 봅니다. 그 시스템을 만들려면 사람의 멘탈 모델, 워크플로, 장애 회고에서 인사이트를 뽑아야 하고, 그 일을 잘합니다.

결정도 같습니다. 가장 좋은 결정은 그 맥락을 가장 잘 아는 사람에게서 나오는데, 많은 조직이 그런 사람을 한 명만 만들어 병목이자 단일장애점으로 만듭니다. 파트마다 그런 사람이 서게 하려면 결정을 기록해 공개하고, 조언을 구하는 의무를 결정권과 함께 두고, 리드는 방향을 정렬한 뒤 장이 실패할 때만 개입해야 합니다. 맥락을 쌓는 비용과 기록하는 비용을 LLM이 낮춰 주는 지금이 그 체계를 만들 때라고 보고, 아래 장치들을 그 방향으로 만들었습니다. 생각은 [좋은 결정은 맥락에서 나온다](https://feel5ny.github.io/2026/08/22/good-decisions-come-from-context/)(2026.08)에 정리했습니다.

### 비즈니스 규칙의 단일 진실 원천(SoT)은 서버에 둔다

같은 규칙을 프론트와 서버 양쪽에 두면 맞추는 비용이 계속 들고 언젠가 어긋납니다. 사람이 조심해서 맞추는 것이 아니라 규칙의 SoT를 한 곳에만 두고 프론트는 그 결과를 표시합니다. 같은 원칙으로 금액 표기 규칙은 코드를 SoT로 삼아 스토리북으로 열었고(1층), 문서는 tech-spec·README·AGENTS.md마다 SoT를 나눴습니다(아래).

- **보험 · 보장분석** (2023, 보험진단): 발병률 나이 제한을 프론트에서 재계산하지 않고 서버 에러 결과를 그대로 노출해 정책이 두 곳에 생기지 않게 함
- **보험 · 보험료 줄이기** (2026, UX 개선): 실손보험료 비즈니스 로직이 프론트에도 있어 QA 대응마다 스펙 복잡성이 커지는 문제를 PM·서버 개발자에게 제기해, 서버가 새 필드를 내려주는 것으로 합의

### LLM이 조직의 맥락을 알게 만들기

흩어진 결정·규칙·스펙을 LLM이 읽는 자리에 쌓고, 리뷰와 스캐폴딩에 쓰게 했습니다. 오래 있었던 사람만 알던 맥락을 누구나 얻을 수 있게 해서 결정할 수 있는 사람의 풀을 넓히는 것이 목적입니다. 이후 망분리와 금감원 제약으로 외부 SaaS를 붙일 수 없게 되면서 도구는 자체 구축으로 고도화했습니다.

- **프로젝트 맥락을 LLM이 닿는 곳으로: 테크스펙 레포 이관** (2026): 구글 독스에 있던 테크스펙을 코드 옆 마크다운으로 옮김. 프로젝트의 맥락이 LLM이 읽을 수 있는 자리에 있어야 하고, 작업 전에 쓰는 문서라 그대로 계획서가 되어 LLM이 청크 단위로 작업하기 좋은 구조가 됨. 표준 생성 스킬로 만들어 팀 공유
- **개발의 방향과 결정 맥락을 LLM이 닿는 곳으로: ADR·회의록 체계** (2026): 개발의 방향성과 의사결정 맥락을 LLM이 알아야 더 많은 맥락 위에서 좋은 결정이 나온다고 보고, 구두로 흩어지던 회의 결정과 액션을 회의록·액션 티켓·ADR로 한 곳에 모음. 회의록은 Jira 티켓으로 관리해 LLM이 접근할 수 있게 하고, 주간 ADR 자동 PR로 결정이 나온 주에 근거까지 남게 함
- **에이전트 하네스의 조직 레이어: 맥락·절차·게이트** (2026): 런타임은 Claude Code를 쓰고, 그 위에 LLM이 조직의 방식대로 일하게 하는 레이어를 레포 안에 구축. 코드만 보고 알 수 없는 도메인 규칙과 외부 제약은 AGENTS.md로(맥락), 페이지 스캐폴딩·스타일 토큰 lint·URL 검토·부채 평가·404 집계처럼 반복되는 작업은 스킬로(절차), PR 전 셀프 리뷰와 윤문 훅은 게이트로 두어 사람이 매번 설명하지 않아도 같은 결과가 나오게 함

- **배포 절차를 모두가 실수 없이 따르게** (2026): 회사가 정한 모노레포 배포 절차가 사람마다 다르게 수행되던 것을, 배포 내역을 손으로 대조하던 단계를 티켓 자동 추출 스크립트로 바꾸고 챕터 필수 프로세스로 만들어 누구나 같은 결과가 나오게 함. build·publish 잡의 참조 시점 차이로 태그가 어긋나던 race를 트리거 시점 SHA 고정으로 제거하고, 점유 배포가 타인 검수를 덮지 않도록 직전 싱크 SHA 기준 ancestor 검사를 넣음. 모노레포 빌드·배포 구조를 이해해야 가능했던 개선

**비개발자가 직접 해도 안전하게**
